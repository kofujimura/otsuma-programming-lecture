第１回

プログラミング言語の歴史とJavaScript

本授業ではJavaScriptのコーディング方法を学びますが、JavaScriptはプログラミング言語の歴史の中でどのような位置づけの言語であり、どのような特徴をもつのか理解しておくことが重要です。ここでは、コンピュータの初期段階から現代までの主なプログラミング言語の変遷を解説します。

1950年代以前：機械語からアセンブリ言語、高級言語へ

プログラミング言語の起源は19世紀に遡ります。特に注目すべきはチャールズ・バベッジの階差機関とエイダ・ラブレスの貢献です。エイダ・ラブレスは階差機関のためのアルゴリズムを記述し、これが世界初のプログラムと見なされています。なお機械式計算機は戦後も1970年頃まで使われており、日本でもタイガー計算機が有名です。

世界初の電子式計算機であるENIACは、米国ペンシルベニア大学で "Project PX" の名で秘密裏に設計が開始され、1946年2月14日に公開されました。

1950年代に入ると最初の高級言語が登場します。FORTRAN（1957年）は科学技術計算のために、COBOL（1959年）はビジネス用途に特化して開発されました。これらはアセンブリ言語のような低級言語に比べて人間が理解しやすい形式を持ち、プログラムの記述が大幅に容易になりました。

1960年代から1980年代：構造化プログラミングとオブジェクト指向

1960年代にはALGOLが登場し、構造化アプローチの基礎が築かれました。構造化プログラミングは、コードの可読性と保守性を向上させるために、ループや条件分岐を明確に記述する手法です。この考え方はPascal（1970年）やC（1972年）に引き継がれました。この頃のハードウェアとしてはIBM System/360や富士通FACOMなどのメインフレームが普及しました。

1980年代にはNEC PC-9801などのPCが販売されるようになり、オブジェクト指向プログラミング（OOP）が注目され始めます。OOPはデータとそれに関連する操作を「オブジェクト」としてまとめる考え方で、プログラムのモジュール化と再利用性を高めました。SmalltalkやC++が代表的で、後にJava（1995年）やPython（1991年）にも影響を与えました。

インターネットの普及とJavaScriptの誕生

1990年代はインターネットの爆発的な普及の時代でした。この時期、Webページに動的なコンテンツを提供するために開発されたのがJavaScriptです。1995年にNetscape（Firefoxの前身）によって開発され、当初はクライアントサイドでのインタラクティブな動作を実現するための言語として設計されました。HTMLとCSSと組み合わせてWebページに動的な機能を追加できる点が強みで、これによりWebは静的な情報提供の場から、ユーザーとの対話を重視するインタラクティブなプラットフォームへと進化しました。

21世紀：PythonとAI、JavaScriptとモバイルアプリ

Pythonは1991年にリリースされましたが、真価が発揮され始めたのは21世紀に入ってからです。シンプルで読みやすい文法がデータサイエンスや機械学習、AIの分野で大きな支持を得ました。GoogleのTensorFlowやMetaのPyTorchなど主要なAIフレームワークはPythonで書かれており、AI開発のデファクトスタンダードとしての地位を確立しています。

一方JavaScriptはWeb開発の中心的な存在から、モバイルアプリ開発へと領域を広げました。React.jsやVue.js、React Nativeの登場により、単一のコードベースでiOS、Android、Webの各プラットフォーム向けのアプリを効率的に開発できるようになりました。

さらにNode.jsはJavaScriptをサーバーサイドで動作させることを可能にし、フルスタック開発を容易にしました。WebAssembly（Wasm）の登場により、ブラウザ上でネイティブコードに近いパフォーマンスを実現し、C、C++、Rustなどとのシームレスな統合も可能になりつつあります。

将来のプログラミング言語

数年先にはAIがコーディングするようになり、人間は一切コードを読まない時代が来るかもしれません。そのときは人間の可読性が必要ないので、これまでとは全く異なる言語が出現するでしょう。このテーマに関してAIと相談した結果はこちら。

デベロッパーツール

JavaScriptの開発の主な実行環境はブラウザです。問題のあるコードはブラウザで実行するとエラーが発生します。このエラーを確認しながらコードを修正するために、Chromeのデベロッパーツール（DevTools）を使用します。これはJavaScript開発者にとって非常に重要なツールです。

開き方

  • ページ上の要素を右クリックして「検証」をクリック
  • Windows/Linux: Ctrl + Shift + I または F12　／　Mac: Cmd + Option + I
  • Chromeのメニューから「その他のツール」→「デベロッパーツール」

主なタブ

  • Elements：HTMLとCSSをリアルタイムで確認・編集できます。要素を選択するとその要素のCSSが表示され、直接編集すると即座にページに反映されます

  • Sources：行番号をクリックしてブレークポイントを設定し、コードをステップ実行しながら変数の値を確認できます
  • Network：ページが行うすべてのネットワークリクエストを監視します。リクエストの内容、応答、所要時間が確認できます（第６回で使います）
  • Application：ローカルストレージやクッキーの中身を確認します（第４回で使います）

初心者のうちから積極的にDevToolsを活用し、コードの問題を早期に発見・修正する習慣をつけましょう。

JavaScriptの概要

JavaScriptは、Webブラウザ上で動作し、主にWebページの動的な操作やインタラクティブな機能を実現するために使用されるプログラミング言語です。

  • インタープリター言語：実行時に逐次解釈されるため、事前にコンパイルを行う必要がありません
  • 動的型付け：変数の型（char, int, floatなど）を明示的に宣言する必要がなく、型は自動的に決定されます
  • イベントドリブン：ユーザーの操作に応じてプログラムが動作します
  • ブラウザベース：HTMLやCSSと連携して、ユーザーの操作に対するリアクションを実現します

各言語の役割

  • HTML：ページの構造と内容を定義します
  • CSS：ページのデザインやレイアウトを担当します
  • JavaScript：ユーザーの操作やイベント発生に基づくインタラクティブな動きを担当します

HTML内でのJavaScriptの配置

JavaScriptは <head> あるいは <body> タグ内に <script> タグを用いて記述します。ただしDOM操作を伴うスクリプトはHTMLの構造を読み込んだ後に処理する必要があるため、</body> タグの直前に配置する方がパフォーマンスやエラー回避の観点から推奨されます。

sample01.html
<!doctype html>
<html lang="ja">
<head>
  <meta charset="utf-8">
  <title>Sample01</title>
</head>
<body>
  <h1>Sample01</h1>

  <script>
    "use strict";
    // ここにJavaScriptコードを記述
  </script>
</body>
</html>
"use strict"; を記述すると、エラー検出が強化されバグを発見しやすくなります。この授業のコードには必ず先頭に書いてください。

コメント

  • 複数行コメント：/* コメント */
  • 一行コメント：// コメント

基本的な命令

JavaScript
alert("Hello, world");        // アラートボックスを表示
console.log("Hello, world");  // コンソールに表示

変数とデータ型

JavaScriptでは変数を let または const で宣言します。let は再代入可能な変数、const は再代入できない定数です。

この授業のルール：まず const で書き、再代入が必要になったものだけ let に変えてください。後から値が変わらないことが一目でわかるので、コードが読みやすくなります。
JavaScript
"use strict";

const age = 25;        // 変わらない値は const
let count = 0;         // 後で count++ するので let

データ型

  • string：文字列（'str', "str"）
  • number：数値（1, 2, 3.14）
  • boolean：真偽値（true, false）
  • object：複数のデータを含む複雑なデータ型（来週詳しく学びます）
  • undefined：値が未定義である状態

最初に文字列が入っていた変数に途中から数値を代入することもできますが、そのようなデータ型の混合はコードが読みにくくなるので避けてください。

JavaScript
const isTrue = true;
const number = 10;
const greeting = "こんにちは";
const doublequote = '"';       // " を扱うときは ' で囲う

文字列はシングルクォーテーション（'）又はダブルクォーテーション（"）で囲います。これらはペアで使用します。シングルクォーテーションで始まってダブルクォーテーションで終わることはできません（エラーになります）。

さらにバッククォート（`）で囲った場合も文字列となります。バッククォートで囲った場合、${ } で囲まれた部分は変数名として解釈され、その変数に格納された値が文字列として埋め込まれます。これをテンプレートリテラルと呼びます。

JSONとJavaScriptのオブジェクトはどう違うのか

見た目はそっくりですが、別物です。ここを区別できると、この先がずっと分かりやすくなります。

  • JavaScriptのオブジェクトはプログラムの中のデータそのもの。キーのクォートは省略できます（{ name: "岩本照" }）
  • JSONはそれを表したただの文字列。キーは必ずダブルクォートで囲む決まりです（{"name":"岩本照"}）。シングルクォートも末尾のカンマも許されません

なぜ文字列にするのか。サーバとの通信も、ブラウザへの保存も、AIとのやりとりも、すべて文字列でしか運べないからです。だから運ぶときは文字列に変換し、使うときはオブジェクトに戻します。

2つの変換関数
"use strict";

// 文字列 → オブジェクト（受け取ったとき）
const data = JSON.parse('[{"name":"岩本照","birthday":"05/17"}]');
console.log(data[0].name);     // "岩本照"

// オブジェクト → 文字列（送る・保存するとき）
const text = JSON.stringify(data);
console.log(text);             // '[{"name":"岩本照","birthday":"05/17"}]'

この2つの関数は、第４回（ブラウザへの保存）、第６回（サーバからの受信）、第８回（AIからの受信）で繰り返し登場します。

ローカルストレージとは

ローカルストレージは、ブラウザ内にデータを永続的に保存するための機能です。localStorage は「オリジン」（ドメイン名とポート番号の組み合わせ）単位でデータを保存し、ブラウザを閉じてもデータが保持されます。

  • 保存容量：オリジンごとに5MB（Cookieは4KB）
  • 保存期間：ユーザーが明示的に削除しない限り永続的に残ります

類似したストレージとして sessionStorage もあります。こちらはタブが開いている間のみ有効です。

localStorage / sessionStorage の解説（Gemini）　／　Webストレージ：ブラウザの記憶術（動画）

基本操作

localStorage の4つのメソッド
localStorage.setItem("key", "value");   // 保存
localStorage.getItem("key");            // 取得（無ければ null）
localStorage.removeItem("key");         // 削除
localStorage.clear();                   // 全削除

保存されている中身は、デベロッパーツールの Application タブ → Local Storage で確認できます。実際に見ながら進めましょう。

ローカルストレージは文字列しか保存できない

ここが今日の山場です。localStorage に保存できるのは文字列だけです。オブジェクトや配列をそのまま渡すと、中身が消えてしまいます。

やってはいけない例
"use strict";

const score = { name: "大妻花子", point: 8 };

localStorage.setItem("score", score);
console.log(localStorage.getItem("score"));  // "[object Object]" ← 中身が消えた

そこで、保存するときは文字列に変換し、読み出すときはオブジェクトに戻します。第３回で学んだ2つの関数の出番です。

JSONを使った正しい保存と読み出し
"use strict";

// ── 保存する ──────────────────────────────
const log = [
  { date: "2026-10-30", score: 8, total: 10 }
];
localStorage.setItem("log", JSON.stringify(log));   // オブジェクト → 文字列

// ── 読み出す ──────────────────────────────
// 何も保存されていないときは null が返るので、"[]" を代わりに使う
const saved = JSON.parse(localStorage.getItem("log") ?? "[]");   // 文字列 → オブジェクト

// ── 追記する ──────────────────────────────
saved.push({ date: "2026-11-06", score: 9, total: 10 });
localStorage.setItem("log", JSON.stringify(saved));
?? は「左が null か undefined なら右を使う」という意味です。1回目の実行では何も保存されていないので、JSON.parse(null) でエラーにならないよう空の配列の文字列 "[]" を渡しています。
これがJSONの本当の役割です。第３回では「他言語とのデータ連携に使う」と説明しましたが、実際には自分のアプリの中ですぐ必要になります。サーバとの通信も、ブラウザへの保存も、AIとのやりとりも、すべて文字列でしか運べない。だから stringify と parse で往復するのです。

選択肢の数をデータに決めさせる

// map：配列の各要素を、別の形に変換した新しい配列を作る
const parts = choices.map(function (text, i) {
  return `<label><input type="radio" name="answer" value="${i}">${text}</label>`;
});
// parts は3個の文字列が入った配列

// join：配列を1つの文字列につなげる

状態推移モデル

前回のクイズは、問題を先頭から順に処理するシンプルな構造でした。しかし実際のアプリでは、ユーザーの選択によって次の画面が変わることがあります。このような「現在の状態によって処理が異なる」プログラミングは、状態推移モデルという方法で管理できます。

状態推移モデルとは

プログラムの進行を「状態」と「遷移」によって管理する手法です。

  • 状態（State）：プログラムが現在どの段階にあるかを示す
  • 遷移（Transition）：条件が満たされたときに次の状態へ移ること
  • 入力（Input）：ユーザーの操作や外部からの情報。これによって遷移が決まる

配列とオブジェクト、どちらを使うか

ここで、第３回で学んだ2つのデータ構造の使い分けを考えます。

配列 [ ]オブジェクト { }
取り出し方番号で取り出す data[0]名前で取り出す data.q1
向いている処理先頭から順に処理するIDを指定して飛ぶ

実装

chart.html
<h2 id="question"></h2>

<script>
  "use strict";

  const chart = { /* 上のデータ */ };

  const questionEl = document.querySelector("#question");
  const choicesEl  = document.querySelector("#choices");
  const resultEl   = document.querySelector("#result");

  let state   = "q1";   // 現在の状態
  let history = [];     // 通ってきた状態を覚えておく（戻る機能用）

  function show() {
    const node = chart[state];
    resultEl.textContent = "";
    choicesEl.innerHTML  = "";

    if (node.choices) {
      // 質問ノード：選択肢のボタンをデータから作る
      questionEl.textContent = node.question;

      node.choices.forEach(function (choice) {
        const btn = document.createElement("button");
        btn.textContent = choice.text;
        btn.addEventListener("click", function () {
          history.push(state);      // 今の状態を記録してから
          state = choice.next;      // 次の状態へ移る
          show();
        });
        choicesEl.appendChild(btn);
      });

    } else {
      // 終端ノード：結果を表示する
      questionEl.textContent = "お疲れさまでした";
      resultEl.textContent   = node.result;
      if (node.image) {
        resultEl.innerHTML += `<br><img src="${node.image}" width="200">`;
      }
    }
  }

  document.querySelector("#back").addEventListener("click", function () {
    if (history.length > 0) {
      state = history.pop();   // 最後に記録した状態を取り出す
      show();
    }
  });

  show();
</script>
「戻る」の仕組み。ブラウザの戻るボタンでは最初に戻ってしまいます。そこで通ってきた状態を history という配列に push() で積んでいき、戻るときは pop() で最後の1つを取り出します。この「積んで、取り出す」構造をスタックと呼びます。

ここまで、データはすべて自分でコードに書いてきました。今日からはデータを外から取ってきます。形は今までと同じ「同じ形のオブジェクトが並んだ配列」です。

非同期処理とは

非同期処理とは、ある処理が完了するのを待たずに次の処理を実行できる仕組みです。ネットワークリクエストやファイルの読み書き、タイマーなどで利用します。これによりブラウザが他の作業をブロックせず、UIをスムーズに動作させ続けられます。

コールバック関数
"use strict";

console.log("開始");

setTimeout(function () {
  console.log("1秒後に実行される");
}, 1000);

console.log("終了");

// 出力順： 開始 → 終了 → 1秒後に実行される

しかし複雑な非同期処理が連続すると、コールバック関数がネストしてコードが非常に読みにくくなります。これをコールバック地獄と呼びます。

コールバック地獄
setTimeout(function () {
  console.log("1つ目の処理完了");
  setTimeout(function () {
    console.log("2つ目の処理完了");
    setTimeout(function () {
      console.log("3つ目の処理完了");
    }, 1000);
  }, 1000);
}, 1000);

Promise

Promiseは、非同期処理の結果を将来受け取るためのオブジェクトです。3つの状態があります。

  • Pending（保留中）：初期状態。処理が完了していない
  • Fulfilled（完了）：処理が成功した。resolve が呼ばれる
  • Rejected（失敗）：処理が失敗した。reject が呼ばれる
Promiseチェーン
"use strict";

function delay(ms) {
  return new Promise(resolve => setTimeout(resolve, ms));
}

delay(1000)
  .then(function () {
    console.log("1つ目の処理完了");
    return delay(1000);
  })
  .then(function () {
    console.log("2つ目の処理完了");
  });

ネストはなくなりましたが、依然として読みにくいと思います。

async / await

async/await は、Promiseをより直感的に扱うための構文です。await を使うと、非同期処理を同期処理のように上から順に書けます。

同じ処理を async/await で書く

なぜ「授業用サーバ」を経由するのか

Google Books APIは、以前はAPIキーなしでも呼び出せました。しかし現在は使えません。実際に試すと、こうなります。

キーなしで直接呼んだ場合
{
  "error": {
    "code": 429,
    "message": "Quota exceeded for quota metric 'Queries' ...",
    "status": "RESOURCE_EXHAUSTED"
  }
}

429 は「回数の上限に達した」という意味です。しかしこれは、みなさんが使いすぎたからではありません。キーを使わないリクエストは、世界中の利用者ぶんが1つの枠にまとめて数えられます。誰かが大量に呼べば、その日は全員が使えなくなります。

ここにAPIキーが存在する理由が現れています。キーがなければ「誰が呼んだか」を区別できないので、サービス側は全員をまとめて制限するしかありません。キーを付ければ「あなたの枠」として管理できます。認証は、利用者を縛るためではなく、区別するためにあります。

エンドポイントとは

WebAPIには、リクエストを受け付ける窓口のURLがあります。これをエンドポイントと呼びます。「この住所に、この形で送ってください」と決められた宛先です。

サービス本来のエンドポイント
Google Bookshttps://www.googleapis.com/books/v1/volumes
OpenAI（第７回で使用）https://api.openai.com/v1/chat/completions
ZipCloud（第９回で使用）https://zipcloud.ibsnet.co.jp/api/search

これらは世界中の開発者が使っている、正真正銘の宛先です。公式ドキュメントに書かれているのもこのURLです。ところが、この授業ではここに直接送りません。

プロキシサーバとは

プロキシ（proxy）は「代理」という意味です。リクエストをいったん受け取り、代わりに本来のエンドポイントへ送り、返ってきたものをそのまま渡す——この中継役をするサーバをプロキシサーバと呼びます。

プロキシを置く理由は5つあります。

  1. APIキーを配らなくて済む：キーはサーバの環境変数だけに置きます。みなさんのブラウザには届かないので、Sandboxを公開しても漏れません
  2. 使いすぎを防げる：1人あたりの上限をサーバ側で決められます
  3. 誰が使ったか分かる：問題が起きたときに追跡できます
  4. キャッシュできる：同じ検索語の結果を覚えておけば、Googleに何度も聞かずに済みます
  5. できることを限定できる：許可した操作だけを通せます
プロキシは特別な技術ではありません。「リクエストを受けて、別の場所へ送って、返す」だけのプログラムです。みなさんが第８回でAIを呼ぶときも、同じ仕組みを通ります。実際のWebサービスでも、外部APIを使うときはほぼ必ずこの形になっています。

  • try/catch を必ず書いてください。エラーでアプリ全体が止まらないように
  • ユーザーに状況を伝えてください。「検索できませんでした。少し待ってお試しください」と画面に出す。無反応が一番困ります
  • どうしても繋がらないときは、検索結果を保存した result.json を読み込めば、通信なしで見た目の調整を進められます（サンプルに同梱）

外の形を、自分の形に変換する

今日いちばん大事な考え方です。外部APIの応答の形は、自分では選べません。Google Booksの応答は次のような深い構造をしています。

Google Books の応答（一部）
{
  "totalItems": １２３,
  "items": [
    {
      "volumeInfo": {
        "title": "ディープラーニング入門",
        "authors": ["山田太郎"],
        "imageLinks": { "thumbnail": "https://..." }
      }
    }
  ]
}

このまま使うと、コードのあちこちに item.volumeInfo.imageLinks.thumbnail のような外部の都合が散らばります。そこで受け取った直後に、自分のアプリの形に変換します。

books.html
"use strict";

// 授業用サーバ（プロキシ）のエンドポイント
//   本来の宛先: https://www.googleapis.com/books/v1/volumes
const BOOKS_API = "https://otsuma-llm-gateway-umber.vercel.app/api/books";

async function search(word) {
  const url = BOOKS_API + "?q=" + encodeURIComponent(word);

  try {
    const res  = await fetch(url);
    const data = await res.json();

    // ここで自分の形に変換する
    const books = (data.items ?? []).map(function (item) {
      const info = item.volumeInfo;
      return {
        title:   info.title ?? "タイトル不明",
        authors: info.authors ?? ["著者不明"],
        cover:   info.imageLinks?.thumbnail ?? "noimage.png"
      };
    });

    // ここから先は、第３回からずっと同じ [{ }, { }] の世界
    show(books);

  } catch (error) {
    console.error("取得に失敗しました:", error);
  }
}

function show(books) {
  document.querySelector("#list").innerHTML = books
    .map(b => `<div><img src="${b.cover}"><p>${b.title}</p>
               <p>${b.authors.join("、")}</p></div>`)
    .join("");
}
?. と ?? はなぜ必要か。APIの応答には欠けているフィールドが普通にあります。Google Booksには表紙画像のない本、著者情報のない本が実際に多く含まれています。info.imageLinks.thumbnail と書くと、imageLinks がない本でエラーになりアプリ全体が止まります。?.（あれば取り出す）と ??（無ければこの値を使う）で、欠けていても動くようにします。配布している result.json で実際に確認してみてください。

会話履歴の構造

AIモデルはステートレス（状態を持たない）です。前回の会話を覚えていません。会話の文脈を理解させるには、過去のやり取りを毎回送信する必要があります。

この「それ」＝Python と理解させるには、履歴を一緒に送る必要があります。

会話履歴も、これまでと同じ「同じ形のオブジェクトが並んだ配列」です。

"use strict";

let conversationHistory = [
  { role: "user",      content: "こんにちは" },
  { role: "assistant", content: "こんにちは！何かお手伝いできますか？" },
  { role: "user",      content: "Pythonを教えて" },
  { role: "assistant", content: "はい、Pythonは..." }
];

// 新しいメッセージを追加
conversationHistory.push({ role: "user",      content: message });
conversationHistory.push({ role: "assistant", content: aiResponse });

// 最新10件のみ取得（トークン数制限への対策）
const recent = conversationHistory.slice(-10);

各メッセージは role（"user" または "assistant"）と content（メッセージの内容）の2つのプロパティを持ちます。slice(-10) は配列の最後から10個の要素を取得します。

APIキーについて

APIキーはWebサービスを利用するための認証情報です。3つの目的があります。

  1. 認証：正規の利用者であることを証明する

セキュリティ上の注意
  • APIキーはパスワードと同じ扱いです
  • GitHubなどのWebサイトには公開しないでください
  • 多くのアプリではサーバー側で管理し、サーバ側からAIモデルにアクセスします

APIの呼び出し

通信には第６回で学んだ fetch() を使います。送信先は、上の図の真ん中——授業用サーバです。

JavaScript
"use strict";

// 授業用サーバ（プロキシ）のエンドポイント
//   本来の宛先: https://api.openai.com/v1/chat/completions
//   OpenAIのAPIキーはサーバ側で付与される。ここには書かない
const CHAT_API = "https://otsuma-llm-gateway-umber.vercel.app/api/chat";

async function askAI(messages) {
  const response = await fetch(CHAT_API, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "Authorization": "Bearer " + settings.token   // 設定画面で入力したトークン
    },
    body: JSON.stringify({                          // オブジェクト → JSON文字列
      model: "gpt-5.6-luna",
      messages: messages
    })
  });

  const data = await response.json();               // JSON文字列 → オブジェクト

  if (!response.ok) {
    throw new Error(data.error || "AIの呼び出しに失敗しました");
  }

  return data.choices[0].message.content;           // 応答の取り出し
}

ここでも JSON.stringify() と JSON.parse()（response.json() が内部で行っています）の往復が使われています。ネットワークを通るものは、すべて文字列です。

応答の取り出し方：data.choices[0].message.content。choices が配列になっているのは、APIに頼めば複数の候補を返させることもできるからです。通常は先頭の1つだけを使います。

エラーへの備え

AIの呼び出しは失敗することがあります。必ず try/catch で囲んでください。

エラー意味と対処
401トークンが正しくない、または再発行済み。発行ページで取り直す
429その日の利用上限に達した。翌日まで待つ
400送ったデータの形が正しくない。messages の中身を確認する
502 / 503OpenAI側の一時的な不調。少し待って再試行する

AIが応答しないことがあります

第６回のGoogle Booksと同じで、こちらに問題がなくてもOpenAI側が一時的に応答しないことがあります。混雑時や、モデルの更新作業中などです。

AIの呼び出しは数秒から十数秒かかります。この間ユーザーは何も起きていないように感じるので、次の3つを必ず入れてください。

  • try/catch：エラーでアプリ全体が止まらないように
  • 「考え中です…」の表示：待っていることが分かるように
  • 送信ボタンを一時的に無効化：連打で何度も課金されないように

  console.error(error);                     // 詳細はコンソールへ

練習：規則性を手順に書き出す

草間彌生の作品を見て、再現したい模様を一つ選んでください。そしてコードを書く前に、次の4点を日本語だけで書き出します。

  1. 描画の最小単位：この模様は何の繰り返しでできているか
  2. 固定されているもの：どの部分でも変わらない要素は何か
  3. 変化しているもの：位置、大きさ、色のうち、何がどう変わっているか
  4. 描画手順：上から順に実行すれば模様が完成する手順を、番号をつけて書く
手順書の例（これがゴールの形）
1. 800×500pxのキャンバスを用意する
2. 背景を赤（R=200, G=30, B=30）で塗る
3. 画面を縦横40px間隔の格子に分ける
4. 各格子の中心に白い円を描く
5. ただし円の直径は、格子ごとに20〜40の範囲でランダムに決める
これでは手順書になりません
赤い背景に、白い水玉をいい感じにたくさん散らす。
だんだん小さくなるようにする。

「いい感じ」「たくさん」「だんだん」は、読む人によって違う絵になります。数値と順序で書けているかを基準にしてください。

手順書には ellipse() や for などのコードや関数名を書かないでください。日本語だけで、誰が読んでも同じ絵になるように書く。これがこの練習の狙いです。

書けたら、その手順書をそのままAIに渡して実装させてみてください。「手順に書かれていないことは補わないでください」と添えるのがコツです。意図と違う絵が出たら、それはAIの失敗ではなく手順書が曖昧だったということです。

ところで、その手順書は草間模様になっているか

いま書いた手順書は、多くの場合こうなっているはずです。

前回の手順書（よくある形）
3. 画面を縦20×横12の格子に分ける
4. 各格子の中心に白い円を描く
5. ただし円の直径は、格子ごとに20〜40の範囲でランダムに決める

これは実装しやすい手順です。しかし出てくる絵は、水玉がきれいに整列した規則的な模様になります。もう一度作品を見てください。水玉は格子に並んでいません。大きさもばらばらで、位置も不規則です。それでいて、水玉同士は重なっていません。

ここが今日の出発点です。「ランダムに置く」と「重ならない」は、同時に成り立たせるのが難しい。格子に並べれば重なりませんが、それは草間模様ではありません。ランダムに置けば草間模様に近づきますが、重なってしまいます。さあ、どうしますか。

重なりをどう判定するか

２つの円が重なっているかどうかは、中心間の距離で判定できます。

重なりの条件
中心間の距離 < 半径A + 半径B     → 重なっている
中心間の距離 ≧ 半径A + 半径B     → 重なっていない

２つの円がちょうど接するとき、中心間の距離は半径の和にぴったり等しくなります。それより近ければ食い込んでいる、というだけの話です。p5.jsには距離を求める dist() があります。

2つの円の判定
const d = dist(x1, y1, x2, y2);
if (d < r1 + r2) {
  // 重なっている
}

置けるまで、場所を変えて試す

判定できるようになったので、方針はこうなります。

考え方
1. ランダムな位置と大きさの円を、候補として1つ作る
2. すでに置いてある水玉すべてと、重なっていないか調べる
3. どれとも重なっていなければ、そこに置いて確定する
4. どれかと重なっていたら、その候補は捨てて、1に戻る

「だめならもう一度引き直す」というこのやり方を棄却法と呼びます。単純ですが、確実に重なりのない配置が作れます。

大事なのは 2 の「すでに置いてある水玉すべてと」 という部分です。1つでも重なっていたらその候補は使えないので、全部調べ終わるまで安心できません。ここが後で効いてきます。
packing.html
"use strict";

const dots = [];        // 置き終わった水玉（第３回で学んだ「オブジェクトの配列」）
let checkCount = 0;     // 距離を計算した回数を数える

function setup() {
  createCanvas(800, 500);
  noStroke();
  placeAll();
  drawAll();
}

// 目標の個数まで置いていく
function placeAll() {
  for (let i = 0; i < 150; i++) {
    const spot = findSpot();
    if (spot === null) break;     // もう置ける場所がなかった
    dots.push(spot);
  }
  console.log("置けた数:" + dots.length + " / 距離の計算:" + checkCount + "回");
}

// 空いている場所が見つかるまで、候補を作っては試す
function findSpot() {
  for (let t = 0; t < 800; t++) {          // 800回試してだめなら諦める
    const r = random(14, 54) / 2;
    const c = {
      x: random(r, width - r),             // 画面からはみ出さない位置
      y: random(r, height - r),
      r: r
    };
    if (overlaps(c) === false) return c;   // 空いていた
  }
  return null;                             // 何度試してもだめだった
}

// 候補が、すでに置いた水玉のどれかと重なるか
function overlaps(c) {
  for (let i = 0; i < dots.length; i++) {
    checkCount++;
    const d = dist(c.x, c.y, dots[i].x, dots[i].y);
    if (d < c.r + dots[i].r + 3) return true;   // +3 は水玉どうしの隙間
  }
  return false;
}

function drawAll() {
  background(200, 30, 30);
  fill(255);
  for (let i = 0; i < dots.length; i++) {
    circle(dots[i].x, dots[i].y, dots[i].r * 2);
  }
}

実行すると、不規則なのに一つも重なっていない水玉が並びます。これが草間模様に近い配置です。

その代償を、数えてみる

コンソールを開いてください。「距離の計算：◯◯回」と出ているはずです。150個置くだけで、数万回の計算をしています。

なぜそうなるかを考えます。overlaps() は、候補ひとつにつきすでに置いた全部と比べます。

何個目を置くとき1回の候補で必要な比較
1個目0回
2個目1回
50個目49回
150個目149回

一度も失敗しなければ、合計は 0+1+2+…+149 でおよそ11,000回で済むはずです。ところが実際の表示は3万回前後になっているはずです。差の2万回は重なって捨てた候補の分です。捨てる候補も、捨てると決まるまでは他の水玉と比べているのです。

そして、個数を増やすと事態はもっと悪くなります。実測するとこうなります。

目標の個数実際に置けた数距離の計算
150150約 31,000 回
300297約 585,000 回
600334約 1,040,000 回
個数を2倍にしただけで、計算は約19倍になりました。「個数×個数÷2」で増えるだけなら4倍のはずですが、それより遥かに悪い。空きが減るほど失敗しやすくなり、失敗するたびに全部と比べ直すという二重の効きかたをするからです。

そして600個を目標にしても、334個しか置けていません。100万回も計算した末に、目標の半分ちょっとで止まっているのです。やりたいことは同じなのに、少し欲張っただけで計算量が爆発し、しかも報われない——これがアルゴリズムを考えるときに常につきまとう問題です。

授業内の練習：限界を体験する

  1. 個数を 150 → 300 → 600 と増やして、コンソールの計算回数を記録してください
  2. どこかで「置けた数」が目標に届かなくなります。何個くらいで頭打ちになりましたか
  3. 水玉の最大サイズ 54 を 110 にすると、頭打ちは早く来ますか、遅く来ますか
  4. 個数を 600 にしたまま、800（諦めるまでの試行回数）を 50 に減らしてください。置けた数と計算回数はどうなりますか

2 で頭打ちになるのは、バグではありません。物理的に置ける場所がもう無いのです。ランダムに置いていく方法では、画面の4割ほどを埋めたあたりで急激に置けなくなることが知られています。どんなに試行回数を増やしても、この壁は越えられません。

4 では、諦めが早いぶん計算は軽くなりますが、置ける数も減ります。計算量と仕上がりのどちらを取るかという取引になっていることを確認してください。

計算量の問題には、対処法があります。遠くにある水玉とは、そもそも比べる必要がありません。画面の右上にある水玉が、左下の候補と重なることはあり得ないからです。

そこで、画面をあらかじめ格子に区切っておき、どのマスにどの水玉があるかを記録しておきます。候補を判定するときは、その候補が入るマスと隣のマスにある水玉だけと比べます。これで比較回数は劇的に減ります。

面白いことに、ここで格子が戻ってきます。ただし今度は「水玉を並べる場所」としてではなく、探す範囲を狭めるための道具としてです。同じ格子でも、使い道がまるで違います。余裕のある人は実装して、計算回数がどれだけ減るか比べてみてください。

createCanvas() の第3引数に WEBGL を指定するだけで、3D空間になります。ただし座標系が変わることに注意してください。

"use strict";

function setup() {

function draw() {

  orbitControl();              // マウスドラッグで視点を回せる

マウスでドラッグしてみてください。orbitControl() の1行だけで、視点を自由に回せます。これだけで「触れる作品」になります。

push() と pop() は必ずペアで使ってください。translate() や rotate() の効果はそれ以降のすべての描画に残り続けます。push() で今の状態を覚え、pop() で元に戻す。これを忘れると、2つ目以降の物体が意図しない場所に飛んでいきます。実際に push()／pop() を消して確かめてみてください。

光と材質

3Dは光がないと何も見えません（正確には、のっぺりした影のない塊に見えます）。光と材質の組み合わせが、作品の印象をほぼ決めます。

命令はたらき
ambientLight(r,g,b)全体を均一に照らす。これだけだと平板に見える
directionalLight(r,g,b, x,y,z)指定した向きから差す平行光。影ができて立体感が出る
pointLight(r,g,b, x,y,z)その位置にある電球。近い面ほど明るい
normalMaterial()面の向きで色が決まる。形の確認用
ambientMaterial(r,g,b)指定した色のマットな材質
specularMaterial(r,g,b)つやのある材質。ハイライトが出る
shininess(n)ハイライトの鋭さ。大きいほど金属的
noStroke()輪郭線を消す。3Dではほぼ必須

動かす

draw() は毎秒60回ほど呼ばれます。frameCount（開始からのフレーム数）を使うと、時間で変化する動きが簡単に書けます。

回転と往復
function draw() {
  background(15);
  orbitControl();
  noStroke();
  ambientLight(80);
  directionalLight(255, 255, 255, -0.5, -1, -0.5);

  push();
  rotateY(frameCount * 0.01);        // y軸まわりにゆっくり回す
  rotateX(frameCount * 0.006);
  ambientMaterial(220, 80, 60);
  box(150);
  pop();

  push();
  // sin() は -1〜1 を往復する。上下運動になる
  translate(250, sin(frameCount * 0.03) * 100, 0);
  ambientMaterial(250, 200, 0);
  sphere(50);
  pop();
}
sin() は往復運動を作るときの定番です。frameCount * 0.03 の 0.03を大きくすると速く、* 100 の 100を大きくすると大きく動きます。この2つの数値だけで、動きの印象を調整できます。

    checkCount++;

    if (d < c.r + balls[i].r + design.packing.gap) return true;

function findSpot() {
  for (let t = 0; t < design.packing.maxTries; t++) {
    const r = random(design.dot.minSize, design.dot.maxSize) / 2;
    const c = {
      x: random(-width / 2 + r, width / 2 - r),      // 原点が中央なので
      y: random(-height / 2 + r, height / 2 - r),
      z: random(-design.packing.depth / 2, design.packing.depth / 2)
    };
    c.r = r;
    if (overlaps(c) === false) return c;
  }
  return null;
}
