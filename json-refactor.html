JSONを背骨にする

じゃんけん・クイズ・診断チャート・API・ローカルストレージを、すべて同じ形のデータで貫く。カリキュラムの順序は変えず、データ設計と記法だけを統一します。

01現状の不整合

資料を通しで読み、データ構造と記法のずれを洗い出しました。いずれも個々には小さいものですが、学生から見ると「毎回ちがう書き方が出てくる」状態になり、データ構造という一本の軸が見えなくなっています。

第６回 ↔ 第１０回

同じクイズアプリなのに、正解番号の起点が違う

第６回の quizData は answer: 1 が第１選択肢を指す1始まり。第１０回のAI生成では「正解の選択肢のインデックス（0, 1, 2のいずれか）」と明記されており0始まりです。第６回のコードに第１０回のデータを流し込むと、全問が一つずれて不正解になります。

第６回

1問版のサンプルコードが構文エラーで動かない

「1問のクイズを作成する方法」の next.addEventListener のコードは、else の後の波括弧が閉じ過ぎており、そのままでは実行できません。複数問版のコードは正しいので、1問版だけの問題です。

第３回

おみくじの手順解説どおりに書くと、毎回同じ結果が出る

「イベントの設定」の節では selectedResult をハンドラの外で確定させているため、何回押しても結果が変わりません。後段の「説明したおみくじのコード例」では showKekka() の内側に入っていて正しく動きます。同じ節の中に、動かない版と動く版が並んでいます。

第３回

JSONを教えた直後の課題が、JSONを一切使わない

第３回はSnow Manの配列で [{...}, {...}] という理想的な形を見せた上で、課題のじゃんけんは 0 / 1 / 2 の生の数値と if-else の連鎖です。せっかく導入したデータ構造が、その日の課題につながっていません。

第６回

ローカルストレージとJSONが、同じ回で教えられて結びついていない

メモ帳が保存するのは素の文字列、最高得点は数値。JSON.stringify() / JSON.parse() でオブジェクトを保存する往復が、授業全体を通して一度も登場しません。これが最も大きな欠落だと思います。

第６回

選択肢が3個に固定されている

option1 / option2 / option3 を個別に取得し、selections[0]〜[2] を手で並べています。データの長さがUIを決める形になっていないため、第１０回でAIに問題数や選択肢数を変えさせた瞬間に破綻します。

第７回

診断チャートの形が、基本と発展課題で別物になる

基本は {question, yes, no}、発展課題のヒントは {question, options:[{text, next}]}。乗り換えの説明がないため、発展課題に進む学生は実質作り直しになります。また終端 t4 だけ image を持ち、レコードの形が揃っていません。

第２回 ↔ 第６回

記法が回ごとに揺れる

配列の宣言が let list1（第３回本文）と const results（同じ回のコード例）で混在。イベントも onclick = と addEventListener の両方が説明なく使われます。第６回では selectedOption.value == quizData[0].answer と、第２回で教えた === ではなく == の暗黙の型変換に依存しています。

02統一する規約

まず、全回で守る約束を決めます。ここが決まれば、あとは各回のコードを寄せるだけです。

項目 統一後 理由
データの基本形 [{ }, { }, { }] 「同じ形のレコードが並ぶ」を全回の基本形にする。第３回のSnow Manの例がそのまま雛形になる。
インデックス 0始まり 配列と一致し、第１０回のAI生成形式とも一致する。第６回を0始まりに直す。
選択肢のキー名 choices selections / options / selectionsList の揺れを一本化。
変数宣言 const 優先 再代入するものだけ let。データ定義は必ず const。
イベント addEventListener onclick = は使わない。第６回以降と実務に合わせ、覚えるものを一つに絞る。
比較 === のみ DOMから来る値は Number() で明示的に変換してから比較する。
保存 JSON.stringify / parse ローカルストレージは文字列しか保存できない、という事実を第６回で必ず教える。
冒頭 "use strict"; 全コード例の先頭に必ず置く（現状は有無が混在）。

あわせて第３回で一度だけ明示したいこと：JSONは「キーを必ずダブルクォートで囲んだテキスト」であり、JavaScriptのオブジェクトリテラルとは別物である、という区別。現状はこの線引きがないまま両方が同じ顔で出てくるため、JSON.parse() が何を変換しているのかが曖昧になっています。

03じゃんけん ── ルールをデータにする

ここが最も効く改訂です。じゃんけんの勝敗を if-else ではなく表で表現します。第３回で教えたばかりの [{...}] が、その日の課題でそのまま使われる形になります。

現状

let randomHand = Math.floor(Math.random() * 3);
// 0: グー, 1: チョキ, 2: パー

if (userHand === randomHand) {
  result = "引き分け";
} else if ((userHand === 0 && randomHand === 1) ||
           (userHand === 1 && randomHand === 2) ||
           (userHand === 2 && randomHand === 0)) {
  result = "勝ち";
} else {
  result = "負け";
}

改訂案

"use strict";

const hands = [
  { name: "グー",   emoji: "✊", beats: 1 },
  { name: "チョキ", emoji: "✌️", beats: 2 },
  { name: "パー",   emoji: "✋", beats: 0 }
];

function judge(myIndex, cpuIndex) {
  if (myIndex === cpuIndex) return "引き分け";
  if (hands[myIndex].beats === cpuIndex) return "勝ち";
  return "負け";
}

何が変わるか：勝敗の知識が beats というデータに移り、判定コードは3行になります。手を5種類（グー・チョキ・パー・井戸・紙）に増やしたくなったとき、現状のコードは条件式を書き直す必要がありますが、改訂案は配列に行を足すだけです。「データを変えれば挙動が変わる」という感覚が、ここで初めて手に入ります。

発展課題の「結果の画像表示」も、emoji を image に差し替えるだけになり、現状のように innerHTML を別途組み立てる話にはなりません。第１０回で「AIに hands 相当の表を作らせる」という展開にもそのまま接続します。

第１０回への接続：AIへのシステムプロンプトに書く出力形式を、この quizData と一字一句同じにします。授業では「第６回で自分の手で書いた形のデータを、今日はAIに書かせます」と言えるようになり、AI活用が新しい話ではなくこれまでの延長として提示できます。

05診断チャート ── 配列とオブジェクトの使い分けを教える場にする

ここは「なぜ配列ではなくオブジェクトなのか」を教える絶好の機会です。クイズは先頭から順に処理するので配列、診断チャートはIDで飛び先を引くのでオブジェクト。この対比を明示します。

あわせて、基本課題と発展課題で形が変わる問題を解消します。最初から choices 形式にしておけば、Yes/Noは「選択肢が2つの場合」にすぎません。

現状（基本と発展で別形式）

  q1: { question: "…", yes: "q2", no: "q3" },
  t1: { answer: "あなたはタイプNです" },
  t4: { answer: "…", image: "https://…" }
};

// 発展課題のヒントでは形が変わる
q1: {
  question: "週末にしたいことは？",
  options: [ { text: "…", next: "q2" } ]
}

06ローカルストレージ ── 欠けている環を埋める

現状、ローカルストレージに保存するのは文字列と数値だけで、オブジェクトを保存する方法が最後まで出てきません。ここに JSON.stringify() / JSON.parse() の往復を入れると、JSONが「必要だから使う」ものになります。

第６回に追加する説明（案）

localStorage は文字列しか保存できません。オブジェクトや配列をそのまま渡すと [object Object] という文字列になり、中身が消えます。

"use strict";

// ✗ 中身が消える
localStorage.setItem("log", { score: 8 });

// ○ JSON文字列に変換してから保存する
const log = [
  { date: "2025-10-31", score: 8, total: 10 }
];
localStorage.setItem("log", JSON.stringify(log));

// 読み出すときは文字列をオブジェクトに戻す
const saved = JSON.parse(localStorage.getItem("log") ?? "[]");
saved.push({ date: "2025-11-07", score: 9, total: 10 });
localStorage.setItem("log", JSON.stringify(saved));

第３回で JSON.parse() を「他言語とのデータ連携に使う」と説明していますが、この例なら自分のアプリの中で今すぐ必要になるので、初学者にとって動機がはるかに明確です。

これに伴い、第６回の課題「最高得点の保存」を「成績履歴の保存」に変更することを提案します。数値1個ならJSONは不要ですが、履歴の配列なら必然的に stringify / parse が要ります。メモ帳の練習で既に求めている「タイトルや日時を複数追加する」という指示とも、ここで初めて噛み合います。

07API ── 外の形を自分の形に変換する

第８回で最も重要な考え方は、fetchの書き方ではなく「外部APIの形は自分では選べない。だから自分のアプリの形に変換する」という点です。これを明示的に教えると、第３回から積み上げてきたデータ設計の意味が完成します。

"use strict";

const res  = await fetch("https://www.googleapis.com/books/v1/volumes?q=" + word);
const data = await res.json();

// Google Booksの深い構造を、自分のアプリの形に変換する
const books = (data.items ?? []).map(item => ({
  title:   item.volumeInfo.title,
  authors: item.volumeInfo.authors ?? ["著者不明"],
  cover:   item.volumeInfo.imageLinks?.thumbnail ?? "noimage.png"
}));

// ここから先は、第３回からずっと同じ [{ }, { }] の世界
books.forEach(book => { /* … */ });

何が変わるか：APIの応答をそのまま画面に流し込むと、コードの中に item.volumeInfo.imageLinks.thumbnail のような外部都合の記述が散らばります。入口で一度変換しておけば、以降のコードはこれまでと同じ形のデータを扱うだけになります。?. と ?? は、APIの応答には欠けているフィールドがあるという現実とセットで教えると腑に落ちます（Google Booksは表紙画像のない本が実際に多く、資料が用意している result.json でも確認できます）。

08統一後に見えてくる流れ

同じ形のデータが、毎回「どこから来るか」だけを変えて登場します。学生には毎回この一行を見せるだけで、全体の位置づけが伝わります。

第３回

自分で書く

hands の表を手で書く。ルールがデータになることを知る。

第６回

自分で書く ＋ 保存する

quizData を手で書き、成績履歴を JSON.stringify() でブラウザに残す。

第７回

形を選ぶ

順に処理するなら配列、IDで引くならオブジェクト。用途でデータ構造を選べるようになる。

第８回

外から取ってくる

APIの応答を、これまでと同じ形に変換して使う。

第１０回

AIに作らせる

第６回と同じ形のデータを、今度はAIに生成させる。形を指定できるのは、その形を知っているから。

この最後の一文が、シラバスに書かれた「AIが生成するコードを責任をもってチェックし、判断する」という到達目標と、そのまま重なります。データの形を自分で設計できる人だけが、AIに正しい形を要求できます。

09作業量の目安

  • すぐ直せるもの：第６回の構文エラー、第３回おみくじのハンドラ位置、let/const の揺れ、'use strict' の欠落。誤りの修正なので判断は不要です。
  • データ形式の統一：第６回を0始まり・choices に変更し、第１０回のプロンプトを同じ形に揃える。サンプルSandboxの差し替えが必要です。
  • 新規追加：第６回のJSON往復の説明と、第８回の変換の節。それぞれ本文半ページ程度。
  • 課題文の変更：第３回（じゃんけんを表で書かせる）、第６回（最高得点→成績履歴）。
